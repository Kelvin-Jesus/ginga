# Development guide

## Prerequisites

| Tool | Notes |
|---|---|
| macOS 14+ (tested on 26.6.2) on Apple Silicon | The target is an M4 MacBook Air; development was done on an M4 MacBook Pro |
| Xcode **or** the Command Line Tools with Swift 6.x | This repo works with the Command Line Tools only (no Xcode) |
| Android (from M4) | JDK 17 (`brew install openjdk@17`), Android SDK command-line tools, `adb` (`brew install android-platform-tools`) |

## Build and test

```sh
cd mac
swift build                      # all targets (debug)
scripts/test.sh                  # all unit tests
scripts/test.sh --filter VirtualDisplayProvider
T2M_INTEGRATION=1 scripts/test.sh --filter RealVirtualDisplay   # creates a real display for about 0.5 s
scripts/build-app.sh             # release build/Tab2Mac.app and build/t2m
```

**Why `scripts/test.sh`:** with only the Command Line Tools installed, SwiftPM doesn't add the swift-testing framework's search and runtime paths. The script passes `-F …/Library/Developer/Frameworks` and the rpaths when `xcode-select -p` points at the Command Line Tools. With Xcode it is a plain `swift test`.

**Test design:**

- **Pure logic is unit-tested with value types:** planner, mode matcher, arrangement, configuration decoding, statistics, capture sizing and metadata parsing.
- **State machines are tested against fakes:**
  - `VirtualDisplayTestSupport` simulates WindowServer's display list, modes, mirroring and a backend.
  - `ShimFakes` are Objective‑C classes with the *exact* selectors and type encodings of the private classes. They let the shim's verification and error handling (exceptions, nil or 0 IDs, rejected settings) run without touching WindowServer.
- **Hardware-touching tests are opt-in** (`T2M_INTEGRATION=1`). Capture tests additionally need Screen Recording permission for the process running them.
- The canary test `privateAPIIsUsableOnThisMac` fails loudly after a macOS update breaks the private interface.

## Running

### The app

```sh
open mac/build/Tab2Mac.app                                   # control panel + menu bar item
open mac/build/Tab2Mac.app --args --create-display           # create the display at launch
open mac/build/Tab2Mac.app --args --create-display --show-preview
open mac/build/Tab2Mac.app --args --config config/examples/galaxy-tab-s11-portrait-120hz.json
```

The virtual display lives at most as long as the app. Quitting the app removes it, and macOS moves its windows back. A display created because a tablet connected is also removed `streaming.displayLingerSeconds` (15 s) after the last tablet leaves.

Settings passed with `--config` apply to that run only: the control panel doesn't save over them, nor over your own `config.json`.

### Headless: `t2m run`

`mac/build/t2m run` is Tab2Mac without its app: the same runtime (virtual display, direct USB, adb with its token, Wi‑Fi, input, pointer channel) with no menu bar or SwiftUI, for the smallest footprint. It reads the app's `config.json` (never writes it), prints a line when something changes, asks Wi‑Fi pairing questions in the terminal, and `--direct` starts the no-router mode. Screen Recording and Accessibility are those of the terminal that runs it.

### The CLI

```sh
mac/build/t2m probe                 # is the private API usable on this macOS? (dumps the runtime interface)
mac/build/t2m displays              # online displays and their modes
mac/build/t2m create --resolution 1440x900 --refresh 120 --position right:center
mac/build/t2m verify --no-capture --report /tmp/m1.json
mac/build/t2m bench-encode --codec hevc --fps 120      # hardware encoder benchmark (no permissions)
mac/build/t2m bench-encode --sweep                     # encoder latency vs power hints, with encoder energy
mac/build/t2m bench-power                              # energy per streaming configuration (~10 min)
mac/build/t2m serve --synthetic                        # stream a test pattern to the tablet over USB
mac/build/t2m receive --port 47800 --seconds 10        # act as the tablet on this Mac (decode + latency)
mac/build/t2m usb                                      # Android devices on USB + AOA support (read-only)
mac/build/t2m usb --switch SERIAL                      # switch one to accessory mode (M6; the tablet prompts)
mac/build/t2m protocol-vectors --out protocol/test-vectors
mac/build/t2m --help
```

### Measuring energy

Power is an acceptance criterion (the reference is Sidecar), so changes that touch the pipeline
are judged by energy, not only latency. Nothing needs root:

- **`t2m bench-power`** launches the app once per scenario and receives on this Mac. The scenarios
  vary display refresh, stream rate, where surplus frames are dropped, and pixel format. It reads
  SoC energy per block over a 20 s steady-state window and compares it with an idle baseline:
  CPU, GPU, **AVE** (the video encoder), memory and display pipes. It also reports the CPU,
  energy and wake-ups of Tab2Mac, `replayd` (ScreenCaptureKit's daemon) and WindowServer. Use
  `--only a,b` to run a subset, `--repeat N` to run more repeats, and `--report r.json` to save
  the raw data.
- **`t2m bench-encode --sweep`** compares the encoder's latency and power hints on the same
  content. The hints are ExpectedFrameRate 1× vs 2×, `RealTime` and `MaximizePowerEfficiency`.
- **Sources:**
  - SoC energy comes from IOReport's "Energy Model" channels. IOReport is private, so it is
    resolved at runtime and linked only into `t2m`, never into the app.
  - Per-process energy comes from `proc_pid_rusage` (`ri_energy_nj`).
  - WindowServer's CPU time comes from `ps`, because it runs as another user.
- **System-wide numbers include everything else running.** A browser playing video or a Gradle
  build adds hundreds of mW. Compare scenarios against the baseline measured in the same run, and
  trust the per-process and AVE figures most.

App launch flags useful for measurements and demos: `--background` starts in the menu bar only,
so no control panel is open (the panel costs CPU while visible). `--serve` accepts a tablet right
away. `--test-pattern` keeps an animated window on the tablet display.

### Streaming to the tablet (USB)

1. On the tablet, enable Developer options › USB debugging, connect the cable, and accept the prompt.
2. On the Mac: Control Panel › Tablet › **Accept the tablet over USB**, or `open mac/build/Tab2Mac.app --args --serve`.
3. Tab2Mac keeps `adb reverse tcp:47800 tcp:47800` in place, using your adb from Homebrew or the Android SDK. It never bundles adb.
4. Open the Tab2Mac app on the tablet and tap Connect.
5. **Without Screen Recording permission** (or to test the tablet side alone): `mac/build/t2m serve --synthetic` streams an animated 2560×1600 pattern. It prints one line per second with the tablet's reported end-to-end and decode latency.
6. **Without the tablet:** `open -n mac/build/Tab2Mac.app --args --background --serve --test-pattern`, then `mac/build/t2m receive --seconds 10 --snapshot /tmp/frame.png`. This runs the whole Mac pipeline (virtual display → capture → HEVC → TCP) into a VideoToolbox decoder on the same clock. It reports fps, frame cadence and display→decoded latency, and the snapshot shows what the tablet would display.

The adb bridge is event-driven. One long-lived `adb track-devices` pushes device changes, and `adb reverse` runs only when a tablet appears or the adb server restarts. Nothing polls.

`t2m` runs AppKit's event loop, because without it CoreGraphics doesn't publish a new display's modes and `NSScreen` doesn't see it.

### M1 sign-off: capture needs Screen Recording

Capture runs under the permission of the *responsible* app. A command started from Terminal is attributed to Terminal, so run capture through the app bundle:

```sh
# 1. Grant once: open the app, click "Grant…", enable Tab2Mac in System Settings,
#    then quit and relaunch it.
# 2. Headless self-test (report + PNG snapshot of a captured frame):
open -W -n --stdout /tmp/t2m-selftest.txt mac/build/Tab2Mac.app --args --self-test \
     --report /tmp/t2m-selftest.json --snapshot /tmp/t2m-frame.png; cat /tmp/t2m-selftest.txt
# 3. Capture benchmark (60 Hz, 10 s; add a --config for 120 Hz):
open -W -n --stdout /tmp/t2m-bench.txt mac/build/Tab2Mac.app --args --benchmark-capture \
     --seconds 10 --report /tmp/t2m-bench.json; cat /tmp/t2m-bench.txt
```

Default report locations: `~/Library/Application Support/Tab2Mac/reports/`.

## Signing and privacy permissions

- `scripts/build-app.sh` signs with `$T2M_SIGN_IDENTITY`, else a `Tab2Mac Development` identity if one exists, else ad-hoc. It always enables the hardened runtime.
- **Ad-hoc signatures change with every build**, and macOS ties privacy grants to the signature, so **Screen Recording must be re-granted after each rebuild**. Run `scripts/create-dev-signing-identity.sh` once to create a self-signed code-signing identity in your login keychain. Rebuilt apps then keep the grant. Read the script first; it modifies your keychain.
- If a stale entry blocks you: `tccutil reset ScreenCapture dev.tab2mac.Tab2Mac`.
- **Distribution:** Developer ID signing + notarization (the private API rules out the App Store).

## Logging and diagnostics

Logs use unified logging, subsystem `dev.tab2mac`. Categories: `virtual-display`, `capture`, `session`, `encoder`, `streaming`, `transport`, `usb`, `security`, `input`, `app` and `benchmark`. Messages are `event.name key=value …`:

```sh
/usr/bin/log stream --level debug --predicate 'subsystem == "dev.tab2mac"'
/usr/bin/log show --last 10m --info --debug --predicate 'subsystem == "dev.tab2mac"'
```

In zsh, `log` is a shell builtin; call `/usr/bin/log`.

**Diagnostics in the app:**

- **Debug preview overlay:** display ID and mode, capture size and format, FPS, capture latency p50/p95, frame-interval jitter, frame counters, process CPU and memory, system GPU utilisation.
- **Control panel › Diagnostics:** the same figures.

## Conventions

- **Strong types:** `PointSize` vs `PixelSize` vs `PhysicalSize`; `MediaTime` for host-clock instants; typed throws for layer errors.
- **Swift 6 language mode:**
  - Display configuration, the session, stream hosts and servers are `@MainActor`.
  - Capture is an actor with a `Sendable` frame fan-out.
  - Work that must keep its order hops through `DispatchQueue.main` (FIFO), not separate `Task`s, which may run in any order (architecture ADR‑13). Display operations and capture starts/stops are chained, each awaiting the previous.
  - Blocking calls (USB control requests, adb) run on dedicated dispatch queues, never on Swift concurrency's cooperative pool.
  - Every `@unchecked Sendable` carries a comment explaining why it is safe.
- **State machines are pure where possible** (`PairingExchange`, `InputInterpreter`, `FrameCadence`, `BitrateController`) and tested without I/O; the classes around them only do I/O.
- **Configuration types decode with defaults**, so configuration files stay sparse and forward compatible. Examples in `config/examples` are validated by `Tab2MacSessionTests`.
- **No third-party dependencies** on the Mac side: native frameworks only.
